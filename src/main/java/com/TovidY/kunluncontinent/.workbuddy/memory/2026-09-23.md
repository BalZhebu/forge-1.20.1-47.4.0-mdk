# 2026-09-23 修复神考第九考后的封神奖励（+1 等级没生效）+ 顺带 3 个隐性 BUG

## 用户报告
"第九考做完后有个动画，过了这个动画玩家 +1 等级，但为什么没加呢？"

## 主 BUG：`addFinalAttrReward` 没有 `dengji` 分支
`GodRegistry` 里每个神都配了：
```java
.addFinalAttrReward("dengji", 1f, "§b神位奖励：百级")
```
（海神 / 修罗神 / 天使神都有）

但 `GodInfo.addFinalAttrReward` 的实现里只处理了
`gongji` / `maxshengming` / `maxjingshenli` / `fangyu` / `baojishanghai` ——
**根本没有 `dengji` 分支**，于是这条奖励被静默丢掉，玩家封神后等级纹丝不动。

对照：同文件里的 `addAttrReward`（考中奖励）**是有** `dengji` 分支的。
→ 典型的"两处各写一遍、其中一处漏了"。

### 修法：抽成共用的 `grantAttr`
`addAttrReward` 和 `addFinalAttrReward` 现在都只调 `grantAttr(player, key, value)`。

### 关键细节：99 级在封神前后语义不同
`PlayerUpgradeSystem.isTupoDengji`：
- `level == 99` → "已经满级，**请封神后再突破**" ← 封神前 99 是硬上限
- `level >= 100 && < 199` → 需要魂环数 ≥ level/10
- `level >= 199` → 真满级

所以新增的 `grantLevels(player, cap, levels)` 里判据是：
```java
if (currentLevel >= 99 && !cap.isGod()) {
    applyLevelStatsOnly(...);      // 封神前卡 99：折算成属性强化
} else {
    processSuccessfulUpgrade(...); // 封神后：99 → 100
}
```
飞升动画结束时 `checkTaskCompletion` 早就把 `isGod` 置成 true 了
（`executeRewards` 之后立刻 `nextGodStage()`），所以最终奖励一定会走"真升级"分支 ✓。

## 顺带修掉的 3 个隐性 BUG

### BUG 2：第九考奖励被发两次
`executeRewards(9, ...)` 里发了一遍，10 秒后 `finalizeAscension` 又发一遍：
- 非积攒型（修罗神/天使神）：第 9 考奖励 ×2
- **积攒型（海神）：1~9 考奖励全部 ×2**（生命值、攻击、暴击伤害、等级……）

修法：`executeRewards` 里**不再发第 9 考奖励**，统一交给 `finalizeAscension`。
（注意保留 `stage < 9` 的两条分支：积攒型只提示、非积攒型立即发。）

### BUG 3：`applyLevelStatsOnly` 复制粘贴错误
```java
capability.setKangbao(capability.getMingzhong() + 1f);   // ← 用命中值去设抗暴
```
改成 `getKangbao() + 1f`。

### BUG 4：物品奖励在背包满时被静默吞掉
`addItemReward` 里 `player.getInventory().add(...)` 的返回值没管。
（天使神第 4 考给 64 个附魔金苹果，背包满就全没了。）
改成 add 失败时 `player.drop(stack, false)`，与 `PlayerAttributeInit` 里的写法一致。

## 没改但值得提一句
`PlayerAttributeCapability.checkTaskCompletion` 里那句
"§6恭喜你，成就XX之位！" 是在**动画开始前**就发出去的，
而 `finalizeAscension` 结尾还有"神格已成，凡躯已脱！"+ 全服通报。
前者算剧透、且和最终播报重复 —— 属于排版口味问题，没动，留给用户决定。

## 校验
`gradlew.bat compileJava --offline` → BUILD SUCCESSFUL。

# 2026-09-23（第二件）修复 NPC 交易物品带 NBT 导致无法堆叠

## 用户报告
"NPC 的交易内容，物品全部带有特殊 NBT `{KlNpcQuality: "白"}`，导致无法和其他正常获得的物品重叠。"

## 根因
`NpcTradeCatalog.generate()` 往**交易结果 ItemStack 上挂了 NBT**：
```java
resultStack.getOrCreateTag().putString("KlNpcQuality", quality.name);
```
这个标签**只用于交易列表的品级染色**（`ModUiRenderHandler.onGuiRender`），
但 NBT 参与 `ItemStack` 的堆叠判定 → 买到的物品永远无法与正常获得的同名物品合并。
（顺带：原版 `MerchantOffer.isRequiredItem` 也用 `NbtUtils.compareNbt` 比 NBT。）

## 难点：不挂 NBT，UI 怎么知道品级？
把展示数据与物品解耦，**按交易内容反查**。用脚本解析了全部 68 条 `TradeEntry`：
**「货币 + 总价 + 物品」三元组零冲突**（`QUALITIES` 池内每条的 currency/cost/item 组合唯一），
所以可以拿它当主键。仅按「物品」反查会有 11 个歧义（NEIDAN1~4、STRONG_POTION、
红火套装、PUTUAN_BLOCK、SOUL_GATHERING_BOTTLE_4 同时属于多个品质），所以物品表只做兜底。

## 改动
1. **`NpcTradeCatalog`**
   - 删掉挂 NBT 那行（原地留 `⚠️` 注释说明为什么不能再挂）。
   - `Quality` 增加 `color` 字段，把原本散在 `ModUiRenderHandler.getQualityColorByName`
     里的 6 个颜色收进来（白/蓝/紫/黑/红/金）→ 品质定义与配色终于在同一处。
   - 新增 `BY_OFFER`（精确）/ `BY_ITEM`（兜底）两张静态反查表，**必须声明在 `QUALITIES` 之后**
     （静态字段按声明顺序初始化）。
   - 新增 `getOfferQualityColor(offer)` / `getOfferQualityName(offer)`；
     反查用 `getBaseCostA()`（原始价）而不是 `getCostA()`（会被 demand 修正），
     且总价要算 `costA.count + costB.count`（>64 时会拆成两格）。
   - 新增旧存档清理：`stripLegacyQualityTag(ItemStack / MerchantOffers / Player)`。
2. **`ModUiRenderHandler`**：改用 `NpcTradeCatalog.getOfferQualityColor(offer)`，
   删掉 `getQualityColorByName` 与不再使用的 `ItemStack` import。
3. **`PlayerNpcEntity.readAdditionalSaveData`**：交易配方是**持久化到 NPC 自身 NBT** 的，
   老存档里的 result 仍带旧标签 → 读档时洗一遍（`getResult()` 返回内部引用，原地删 tag 有效）。
   （**只保留这一处**：每次 NPC 读档跑一次、约 12 次循环，开销可忽略，
   而且不洗的话老存档 NPC 卖出的物品**仍然带 NBT**、等于没修。）

## ⛔ 按用户要求砍掉的部分
原本还加了「玩家登录时扫背包 + 末影箱洗掉已买到的带标签物品」，
**用户明确否决**（"不用补上旧存档里玩家身上已买到物品的清理，没必要浪费性能，直接搞现在的交易就行"）
→ 已删除 `stripLegacyQualityTag(Player)` 与 `stripFromContainer`，以及
`PlayerUpgradeEventListener` 里的调用和 import。
**结论：这个项目里不要主动加"登录时遍历背包"之类的补漏逻辑，用户很在意这类无谓开销。**

## 修这个 BUG 时的两个技术要点
- **删完 key 若 tag 变空，必须 `stack.setTag(null)`**。留个空 CompoundTag 一样
  `hasTag() == true`，照样堆叠不了 —— 这是最容易漏的一步。
- `MerchantOffer` 的 `baseCostA / costB / result` 在网络（`MerchantOffers.writeToStream`
  用 `writeItem`）和 NBT（`createTag` 用 `ItemStack.save`）两条路上都是完整保留的，
  所以内容反查在客户端和读档后都成立。
- 顺带确认过一条可复用的 API 事实：**`Inventory.setChanged()` 只累加内部计数器、
  不同步客户端**，改完物品 NBT 要显式 `serverPlayer.inventoryMenu.broadcastChanges()`。

## ⚠️ 工具坑（重要）
**同一个文件的多处 Edit 并行发出时会丢改动。** 这次一次发了 5 个 Edit 改
`NpcTradeCatalog` 的 6 个 Quality 常量行，只有 2 个生效、3 个被静默丢弃（编译才报出来）；
另一批改 `ModUiRenderHandler` 的两个 import 也丢了 1 个。
→ **同一文件的多处修改必须逐个 Edit（分次调用），改完 grep 复查。**

## 校验
`gradlew.bat compileJava --offline` → BUILD SUCCESSFUL（3 个构造器参数错误已修）。

# 2026-09-23（第三件）魂环"开启方式"新增 3 种动画 + 修掉第一人称渲染的坐标 bug

## 用户需求
配置界面新增一个按钮切换魂环开启动画；3 种开启方式：
第 1 种 = 原有展开方式，第 2 种 = 从头上往下展开，第 3 种自定（要美观、有气场，**禁止用粒子代替**）。

## 关键前提：先搞清楚 Post 事件的 PoseStack 空间
`RenderPlayerEvent.Post` 是在 `LivingEntityRenderer.render` 里触发的，但**位置很关键**：
```
pushPose() → setupRotations/scale(-1,-1,1)/scale(0.9375)/translate(0,-1.501,0)
→ model.renderToBuffer() → … renderLayers … → popPose()   // 第 135 行
→ super.render() → post(RenderLivingEvent.Post)            // 第 137 行
```
`PlayerRenderer.render` 同理：Post 在 `super.render()` 之后。
⇒ **事件里的 PoseStack 没有任何模型变换**，就是"实体渲染器刚进栈"的相机相对坐标：
**原点在脚底、1 单位 = 1 格**。（社区写法 `translate(0, getBbHeight(), 0)` 用的就是格。）
所以 `renderHunhuanFast` 里的 `heightOffset = 0.25 + count*0.02` = 脚踝上方 0.25~0.43 格，对得上。

## 顺带修掉的真实 BUG
第一人称补渲染（`renderFirstPersonRings`）里我上次**多叠了一串模型变换**
（`180-bodyYaw / scale(-1,-1,1) / 0.9375 / translate(0,-1.501,0)`），
导致第一人称的魂环比第三人称**高约 1.2 格**（`-1.501` 在 Y 翻转的帧里变成 +1.41 格，
再被 `0.25*0.9375` 抵掉一点），并且第 10 枚起的神环"背后"方向会反向。
按上面的源码结论，这段链路整段删掉，只留 `translate(px-cam.x, py-cam.y, pz-cam.z)` 即可。
（`RenderLevelStageEvent` 与 Post 本就是同一套空间，所以是"直接等价"，不是"近似"。）

## 3 种样式的实现（全部纯几何变换，零粒子）
统一收在 `PWRenderPlayerEvent.openAnim(...)`，返回 `OpenAnim(x,y,z,spinDeg,scaleMul,alphaMul)`：
- **0 逐环展开**：`scaleMul = progress`（与原逻辑等价），额外加了起手 25% 的淡入。
- **1 天降落位**：`y = getBbHeight()*1.35 * (1 - easeOutBack(t))` —— 从头顶之上垂落，
  落定带一点回弹；下落途中 `+240° * (1-easeOutCubic)` 的额外自转，尺寸 0.30→1。
- **2 旋绕归位**（自定）：每枚环用**黄金角 137.508° × 序号**取方位，
  起始半径 = 该环半径 × 3.4 格，`(1-easeOutCubic)` 收束到 0；同时下沉 0.9 格、
  自转 `720°*(1-easeOutCubic)` 由快到慢定住，尺寸用 `easeOutBack` 收到 1（3% 过冲）。
  读起来就是"魂环从四周盘旋飞入、转着落位"，气场足且完全是几何运动。

`progress >= 1` 时 `openAnim` 直接返回 `IDLE`（全零偏移）→ **静止观感与改动前一致**，
不会因为加样式而改变常态画面。三种样式都**不用任何粒子**。

## 数据链路
- `PlayerAttributeCapability.hunhuanOpenAnim`（int，setter 内 clamp 0~2）+ NBT `HunhuanOpenAnim`。
- `PacketChangeHunhuanAnim`（C→S，只用于持久化，收到后 `SynsAPI` 回同步）+ `NetworkHandler` 注册。
- ⚠️ 样式要**跟着 `SyncWuhunDataPacket` 走**（新增 int 字段），存在 `EntityWuhunCache.animStyle`，
  由 `PlayerHunhuanAPI.broadcastWuhunRings` 从 capability 取出后广播 ——
  这样**别人的客户端也按你的样式播开场动画**，而不是只对自己生效。
- `ConfigScreen` 按"伤害显示"那种**循环切换项**加：`index` 用 -2 占位，
  `onClick` 里 `(当前+1) % HUNHUAN_ANIM_COUNT`，本地先 set 再发包让按钮文字立刻更新。
- 样式名数组放渲染侧 `PWRenderPlayerEvent.ANIM_STYLE_NAMES`，UI 直接引用，避免两处写中文。

## 顺手修的小瑕疵
`renderShenhuanFast` 原来 `scale = 0.22 * progress`，而 `progress >= 1` 时才乘 `(0.4+count*0.12)`，
展开结束那一帧会从 0.22 **跳到** 0.326（肉眼可见的"啪"一下）。
现在把枚数倍率并入基础尺寸、再乘 `anim.scaleMul()`，收官连续无跳变。

## 校验
`gradlew.bat compileJava --offline` → BUILD SUCCESSFUL。
