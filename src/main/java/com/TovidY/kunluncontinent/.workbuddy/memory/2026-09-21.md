# 2026-09-21（重做）吸收动画改为「魂环贴图粒子」

原版粒子拼出来的圆环只是一圈光点，看不出是"魂环"；而魂环本来就有贴图。

## 正确做法：自定义粒子
新增：
- `Init/ModParticles.java` —— 注册两个 `SimpleParticleType`：
  `hunhuan_ring`(魂环) / `shenhuan_ring`(神环)
- `assets/kunluncontinent/particles/{hunhuan_ring,shenhuan_ring}.json` —— 粒子贴图定义
- `assets/kunluncontinent/textures/particle/{hunhuan_ring,shenhuan_ring}.png`
  —— 从 `textures/picture/{particletext,shenhuan}.png` 复制并**2×2 盒式降采样**
  （1024²→512²、860²→430²，体积 -70%，避免粒子图集塞不下；透明通道已回读验证 0..255）
- `entity/hunhuan/HunhuanRingParticle.java` —— 核心：`extends TextureSheetParticle`
  - **环绕模式**：每 tick 把自己摆到「center + 半径 + 角度」上，角度累加 → 真绕玩家转，
    且玩家移动时跟着走。半径/角速度/起始高度/上升速度/自转速度/寿命/缩放全部可配。
  - **自由模式**：按初速度飞散 + 阻尼（爆发 / 塌缩用）
  - 恒全亮（`getLightColor` 返回 0xF000F0）、半透明混合、末尾淡出
  - Provider 构造时把 `SpriteSet` 缓存进静态字段，供网络包直接 spawn 使用
- `network/server/PacketHunhuanParticles.java` —— S2C，只带
  {anchorId, mode(OPEN/ORBIT/BURST/COLLAPSE), tier, phase}：
  **一个包让客户端生成几十枚魂环**，比 `sendParticles` 一个粒子一个包省得多

重写：
- `HunhuanAbsorbFx` —— 彻底不用原版粒子了，只负责发粒子包 + 播广播音效
  （保留 Tier 档位表：阈值/尺度/中文名/主题色）
- `ClientHunhuanAbsorbManager.onParticles(...)` —— 各模式的具体生成参数
  （环绕批：半径 0.75~1.7、高度 0.15~1.65、角速度 ±0.05~0.125、寿命 28~44、三成收束七成张开）
- `NetworkHandler` 注册新包；`KlMain` 注册 `ModParticles` + `RegisterParticleProvidersEvent`

## 自定义粒子的完整接入链路（以后照抄）
1. `DeferredRegister<ParticleType<?>>` 注册 `SimpleParticleType`，名字必须与
   `assets/<modid>/particles/<name>.json` 的**文件名一致**，否则图集里拿不到 sprite
2. 贴图放 `assets/<modid>/textures/particle/<name>.png`（粒子图集只收这个目录）
3. JSON：`{"textures": ["<modid>:<name>"]}`
4. 客户端在 `RegisterParticleProvidersEvent#registerSpriteSet` 注册 Provider
   （放在 `@Mod.EventBusSubscriber(value = Dist.CLIENT)` 的嵌套类里，
   这样专用服务器不会加载 `net.minecraft.client.particle.*`）
5. 想绕某实体转：Provider 里把 SpriteSet 存到静态字段，
   再由网络包调用静态 spawn 方法 —— **原版 `addParticle` 的 6 个 double 传不下这么多参数**

## 其他经验
- 无 PIL 时用纯 python 处理 PNG：zlib 解 IDAT + 手动反滤波（filter 0~4）+ 重新编码
  （IHDR/IDAT/IEND + crc32）。2×2 盒式平均降采样好写且质量够。改完必须回读验证。
- 粒子贴图**务必带 alpha**（用 PNG 头第 25 字节的 color type 判断，6=RGBA；
  再扫一遍 alpha 极值确认不是全 255），否则粒子会渲染成不透明方块。

# 2026-09-21（第三次修）魂环躺平：重写粒子 render

## 用户反馈
"不行，你把魂环立起来了，这玩意应该是平方（平放）的。"
→ 魂环应该像呼啦圈一样**横着**套在身上，不是竖着的圆盘。

## 根因
**粒子贴图默认是公告板（billboard）—— 永远正对摄像机**。
`SingleQuadParticle.render` 用 `camera.rotation()` 当四边形的旋转，
所以贴图必然"竖着面对你"，不管内容是什么。
想让粒子躺平，**必须重写 `Particle.render`**。

## 做法（`HunhuanRingParticle.render`）
```java
Quaternionf rot = new Quaternionf()
        .rotateY(spin)          // 绕世界 Y 自转
        .rotateX(TILT);         // TILT = +π/2，把局部 +Z 法线转到世界 +Y
```
- **JOML 的 `rotateX/rotateY` 是右乘**（`q = q * R`），后调用的先作用于顶点。
  所以 `rotateY(a).rotateX(π/2)` = `Ry(a) · Rx(π/2) · v` → 先翻平，再自转，自转轴保持竖直。✓
- 符号：绕 X 轴旋转 θ 把 (0,0,-1) 映射到 (0, sinθ, -cosθ)。
  四边形按 `(-1,-1)→(-1,1)→(1,1)→(1,-1)` 绕序，法线是**局部 -Z**，
  所以要用 **+π/2**（θ=+π/2 → 法线 (0,1,0) 朝上）。用 -π/2 会朝下。
- 平移量仍用 `Mth.lerp(partialTick, xo, x)` 减去 `camera.getPosition()`，
  和父类一致。

## 平躺四边形必须画两遍
`ParticleRenderType.PARTICLE_SHEET_TRANSLUCENT.begin()` **不设置面剔除状态**
（只有 TERRAIN_SHEET 显式…实际它也没写），cull 是上一段渲染遗留的、不确定。
所以正反两面各输出一次同样的 4 个顶点（反过来绕序 + 对应 UV）。
就一片四边形，开销可忽略，但能保证任何 cull 状态下都看得见。

## 其他必须注意
- `quadSize` 是**半宽**，四边形边长 = `2 * quadSize`。
  实测魂环贴图图形占满整张图的 96%，所以**显示直径 ≈ 1.9 × quadSize**。
  本次尺寸改成 quadSize 0.78(凡品) → 1.12(神赐)，即直径约 1.5 → 2.1 格。
- 重写 render 后**包围盒还是原来那个 0.2 的小盒子**，会被裁剪掉大半 →
  构造时 `setSize(baseSize*2.2F, ...)` 放大 + `shouldCull()` 返回 `false`。
- 自转从"屏幕内滚"改成"绕竖直轴转"：`roll` 现在喂给 `rotateY`，速度 0.05 rad/tick。

## 顺手查清的项目事实
`PWRenderLivingEvent.renderHunhuan` 里画的裸顶点是 **±6 单位**。
它被 `RenderLivingEvent.Post` 调用，而那个时点的 PoseStack 是
**实体模型空间（16 单位 = 1 格）**，不是世界尺度 → ±6 单位 = **0.75 格**，
再乘 `renderHunhuanAttribute` 的 0.4（十年）~ 2.0（亿年）。
所以 mod 自己给怪物画的魂环是 0.3 ~ 1.5 格直径、贴在脚边（heightOffset 0.22/16）。

# 2026-09-21（第四次修）年限配色 + 动画放大

## 用户反馈
"颜色不对，根据吸收魂环的年限把魂环的颜色一起变了，然后动画更大方一些，
 不用小小的魂环一个上下晃。"

## 关键实测：魂环贴图是**纯白**的
用 python 解 PNG 统计不透明像素：
- `hunhuan_ring.png` 平均色 RGB=(244,244,244)，**饱和度中位数/90分位/最大全是 0.00**
- `shenhuan_ring.png` 平均色 RGB=(238,238,238)，同样全 0

→ 贴图是纯白图形（只有 alpha 变化）。**所以粒子染色就是"乘什么颜色得什么颜色"**，
  之前 `tint()` 只往主题色靠六成、留白打底，反而把颜色兑淡了 —— 这就是"颜色不对"的根因。
  **修正：直接返回主题色原值。**

## 配色表对齐 mod 自己的口径
`PWRenderLivingEvent.renderHunhuanAttribute` 已经有一套按年限的 `setShaderColor`：

# 2026-09-21（第五次修）吸收成功收束动画 + 隐身被骑的魂环实体

## 需求
1. 吸收**成功**时：魂环先到玩家**头顶且比较大**，然后慢慢缩小 + 下移，飞入玩家身体内。
2. 吸收期间把**玩家骑着的那个魂环实体隐形**（地面上的环压在身下很怪）；
   玩家中途下车（中断）要恢复显示。

## 判定"成功 vs 中断"靠原版同步状态就够
- **成功**：服务端 `HunhuanEntity.handleAbsorbed()` → `discard()` → 魂环实体从客户端消失。
- **中断**：玩家自己下车，**魂环实体还在**。
→ 所以「魂环实体没了」= 成功，「实体还在但玩家不骑了」= 中断。零发包。
- 但两个包（乘客变更 / 实体移除）到达顺序不确定，所以**不能立刻下结论**：
  粒子进入 `SETTLING` 阶段，宽限 `SETTLE_GRACE = 4` tick，期间实体消失就判成功。

## 粒子改造成阶段机（`HunhuanRingParticle`）
```java
enum Phase { FOLLOW, SETTLING, CONVERGE, FADE }
```
- `FOLLOW`：玩家骑着 → 上下扫过 + 缩放脉动。
- `SETTLING`：宽限 4 tick 判定。
- `CONVERGE`（收束，共 22 tick，前 27% 是"升顶放大"，后 73% 是"缩小下移飞入"）：
  - 起手关键帧取进入收束时的当前位置/尺寸，缓出插值到「脚底 +2.30 格、尺寸 ×1.5」；
  - 再二次曲线下移到「脚底 +0.95 格（身体中心）」，尺寸按 `1 - k²` 收缩
    → 前半段保持大、后半段才明显缩小；下移用 `k²` → 慢慢下、末尾加速"飞入"；
  - 自转加速 `×3`，最后 30% 淡出。
- `FADE`：中断，12 tick 淡出。
- `phaseTicks` 允许从负数起步 —— `/particle` 指令生成的默认形态用 `phaseTicks = -60`
  实现"原地悬浮 60 tick 再淡出"。

粒子同时记住 `riderId`（玩家）和 `ringId`（魂环实体）两个 id，自己查自己判。

## 隐形魂环实体：改 `HunhuanRender`
`HunhuanRender extends EntityRenderer<HunhuanEntity>`，是魂环实体的渲染器。
```java
if (!entity.getPassengers().isEmpty()) return;   // 有人骑着就不画
```
- 用**乘客**判断，不用 `isInvisible()` —— 因为 `EntityRenderer` 本来就不检查 `isInvisible()`，
  自己写也要加这个判断；用乘客更省，而且**玩家一下车自动恢复显示**，不需要任何状态同步。
- 乘客是原版同步的（`ClientboundSetPassengersPacket`），所以别的玩家骑上去本地也能正确隐藏。

`gradlew.bat compileJava --offline` → BUILD SUCCESSFUL。

# 2026-09-21（第六次修）吸收后新魂环不显示的同步问题

## 症状
吸收完成后，新魂环**不会立刻出现在玩家身上**，必须手动"关开一次魂环"（切换武魂）才显示。

## 根因：客户端有一份"永不失效"的渲染缓存
玩家/怪物的魂环渲染在 `event/client/PWRenderPlayerEvent`，它读的是
**按实体 UUID 缓存的一份快照** `entityWuhunCacheMap`（`Map<UUID, EntityWuhunCache>`，
里面存 `List<HunhuanRenderData>`）。这份缓存**只在三个时机刷新**：
1. 玩家登录 / 换维度 → `startOpenAnimation(player)`
2. 手动开关魂环 → `CPacketQiehuanWuhun` → `startOpenAnimation` / `sendCloseNotification`
3. 收到 `SyncWuhunDataPacket` / `SyncNpcWuhunPacket`

`renderPlayerEventPost` 里只对**本地玩家**且在 `cache == null` 时才懒加载一次：
```java
if (cache == null && entity.equals(localPlayer)) { loadFromCapability(); }
```
→ 缓存一旦建起来就再也不刷新。**吸收魂环这条路径从来没人广播过**，
所以缓存里还是旧列表（甚至没有该玩家）→ 要手动关开一次才更新。

## 修复
- 新增 `PlayerHunhuanAPI.broadcastWuhunRings(ServerPlayer player, boolean playAnimation)`
  —— 收集当前魂环年限列表并广播 `SyncWuhunDataPacket` 给同维度所有玩家（含自己）。
- `HunhuanEntity.handleAbsorbed()` 里在 `playComplete` 之后调用
  `broadcastWuhunRings(serverPlayer, false)`（`false` = 不重播出场动画，
  否则已有的魂环会陪着重播一遍）。
- 顺手把 `PWRenderPlayerEvent.startOpenAnimation` 服务端分支里那段重复的
  收集 + 广播逻辑换成调用同一个工具方法（`playAnimation = true`）。

## 顺带确认的两个语义（重要）
- `PlayerAttributeCapability.getWuhunList()` 在 `hunhuankuaiguan < 0`（**武魂显示关闭**）时
  返回 `null` → 广播出去就是空列表 → 客户端 `updatePlayerWuhunData` 会把缓存删掉。
  所以"玩家把魂环显示关掉了，吸收后又被顶开"这个坑天然不存在，**不用额外加判断**。
- `hunhuankuaiguan` = **当前显示的武魂下标**，`-1` = 关闭。
  开关逻辑在 `network/client/CPacketQiehuanWuhun`：
  依次 +1 循环，超过最后一个就置 -1。

## 校验
`gradlew.bat compileJava --offline` → BUILD SUCCESSFUL。

# 2026-09-21（第七次）新增配置开关：第一人称魂环（默认关）

## 需求
吸收动画的粒子在第一人称能看到，但玩家**自身**的魂环在第一人称看不到。
要把"玩家身上的魂环"改成第一人称可见，并用一个新配置开关控制，**默认关闭**。

## 根因：原版第一人称根本不渲染本地玩家实体
`LevelRenderer` 的实体循环里有一条判定（源码 line 1227）：
```java
if ( ... && (entity != pCamera.getEntity() || pCamera.isDetached()
             || pCamera.getEntity() instanceof LivingEntity && ((LivingEntity)pCamera.getEntity()).isSleeping())
     && (!(entity instanceof LocalPlayer) || pCamera.getEntity() == entity || ...) ) {
```
第一人称时摄像机是**贴在自己身上**的（`isDetached()` 为 false），
第一条判定直接为 false → **本地玩家实体整个被跳过** → `PlayerRenderer.render` 不执行 →
`RenderPlayerEvent.Pre/Post` 根本不触发。所以挂在那个事件上的魂环渲染在第一人称永远看不到。

## 解法：换钩子自己补一份
`PWRenderPlayerEvent.renderFirstPersonRings(RenderLevelStageEvent)`，
只处理 `Stage.AFTER_ENTITIES`，条件：
- `mc.options.getCameraType().isFirstPerson() && mc.getCameraEntity() == mc.player`
- 配置 12（第一人称魂环，默认关）+ 配置 2（自身魂环显示）都开着
- 缓存为空时自己懒加载一次（第一人称下 `renderPlayerEventPost` 不跑）

**核心技巧：不要猜模型空间用的是什么单位，把变换链一字不差复刻。**
```java
poseStack.pushPose();
poseStack.translate(player.getX() - camPos.x, player.getY() - camPos.y, player.getZ() - camPos.z);
float bodyYaw = Mth.rotLerp(partialTick, player.yBodyRotO, player.yBodyRot);
poseStack.mulPose(Axis.YP.rotationDegrees(180.0F - bodyYaw));
poseStack.scale(-1.0F, -1.0F, 1.0F);
poseStack.scale(0.9375F, 0.9375F, 0.9375F);      // PlayerRenderer.scale
poseStack.translate(0.0F, -1.501F, 0.0F);        // LivingEntityRenderer 原样
renderRingsForEntity(player, cache, poseStack, partialTick);
poseStack.popPose();
```
这样第一人称与第三人称**必然**同一套空间，不用去推导"1 单位是 1 格还是 1/16 格"
（我这次在这上面绕了很久，最后发现最优解是直接抄）。

## 配置系统（加新开关的标准做法）
- `PlayerAttributeCapability.configFlags` 是 **long 位掩码**，默认 `0xFFL`（bit0~7 开）。
  `isConfigOpen(i)` 读位、`toggleConfig(i)` 异或位。→ **索引 12 默认就是关的**，不用改默认值。
- 加开关只改 `screen/attribute/config/ConfigScreen`：
  1. `initMainPage` 的 `rawItems` 加 `new ConfigItemData("名字", 12)`；
  2. `getToggleTooltip` 加 `case 12 -> ...`。
  按钮的开关逻辑、消息、发包都是循环里统一处理的，不用动。

## 踩坑
- Gradle 偶发 `Failed to validate certificate for host 'https://libraries.minecraft.net/'`，
  **与代码无关**（插件 apply 阶段联网校验），重试即可。
  加 `"-Dnet.minecraftforge.gradle.check.certs=false"` 可以绕过；
  **但 PowerShell 里这个参数必须加引号**，否则 `-D...` 会被当成任务名：
  `Task '.minecraftforge.gradle.check.certs=false' not found`。

## 校验
`gradlew.bat compileJava --offline` → BUILD SUCCESSFUL。

# 2026-09-21（第八次）修复第一人称魂环移动时疯狂抽动

## 症状
第一人称能看到魂环了，但**一移动就疯狂抽动**。

## 根因：位置没做 tick 插值
我原来写的是：
```java
poseStack.translate(player.getX() - camPos.x, player.getY() - camPos.y, player.getZ() - camPos.z);
```
`getX()` 拿到的是**当前 tick 的快照**，而画面里其它一切（相机、实体、粒子）都是
`Mth.lerp(partialTick, xOld, x)` 插值绘制的 —— 只有这圈魂环每 tick 跳一整格位移。
环本身只有 0.2~0.7 格大，跳一步就是好几个环的宽度 ⇒ 观感就是"疯狂抽动"。

## 修法（与 `LevelRenderer.renderEntity` 完全一致）
```java
double px = Mth.lerp(partialTick, player.xOld, player.getX());
double py = Mth.lerp(partialTick, player.yOld, player.getY());
double pz = Mth.lerp(partialTick, player.zOld, player.getZ());
poseStack.translate(px - camPos.x, py - camPos.y, pz - camPos.z);
```

## 经验（通用规则）
**在 `RenderLevelStageEvent` 里画"跟随实体"的东西时，位置必须自己插值。**
这个事件只给一个相机相对的 PoseStack，**不会**帮你把实体位置插值 ——
「当前 tick 坐标」和「带 partialTick 的插值坐标」差多少，就是每 tick 抖多少。

顺带确认过一个不用管的地方：第一人称的走路视角晃动（`bobView`）会改
`camera.getPosition()`，而我是用 `camPos` 反推环的位置，所以环跟着相机一起晃、
和世界其它东西同相 —— 不会有额外相对抖动，不需要补偿。

## 校验
`gradlew.bat compileJava --offline` → BUILD SUCCESSFUL。
